# 0002. 모노레포 + 서비스 분리

- 상태: 승인
- 날짜: 2026-11-12

## 맥락

이 프로젝트는 성격이 다른 구성요소 여럿으로 이뤄진다.

- 법제처 API 수집 (주기적 배치)
- 청킹·임베딩·그래프 적재 (무거운 데이터 처리)
- 검색·답변 API
- MCP 서버
- 웹 UI
- 평가 스크립트
- 인프라 정의 (Docker Compose, Helm, Terraform)

이들을 **실행 단위(서비스)**로 나눌지, **코드 저장소**로 나눌지 정해야 한다.
여러 팀이 일하는 조직에서는 서비스마다 저장소를 나누는 경우가 많지만, 이 프로젝트는 **혼자** 개발한다.

## 결정

**서비스는 나누고, 저장소는 하나(모노레포)로 시작한다.**

```
law-ontology/
├── apps/
│   ├── collector/    Spring Boot — 법제처 API 수집 → Postgres 원장
│   ├── ingest/       Python      — 조문 분해 · 청킹 · 임베딩 · Qdrant/Neo4j 적재
│   ├── api/          Spring Boot — 검색 · 답변 생성 API
│   ├── mcp-server/               — MCP 도구 제공
│   └── web/          Next.js     — 채팅 UI
├── eval/             Python      — 평가셋 · 채점 스크립트
├── infra/            docker-compose · Helm · Terraform
└── docs/             PRD · ADR · 설계 문서
```

- 각 서비스는 **별도 컨테이너**로 실행·배포한다.
- 언어 선택: 수집과 API는 주력 스택인 **Spring Boot**, 데이터 처리와 평가는 생태계가 풍부한 **Python**.
- 서비스 간 데이터 계약(청크 스키마, 정식 키 형식 등)은 `docs/`에 문서로 고정하고, 바꿀 때는 같은 커밋에서 양쪽을 함께 고친다.
- CI는 경로 필터로 **바뀐 서비스만** 빌드·테스트한다.

## 저장소를 분리하는 기준

아래 중 하나에 해당하면 그때 별도 저장소로 분리하고, 분리 이유를 새 ADR로 남긴다.

1. **배포 대상이 다르다**: 예) Claude Code 플러그인은 마켓플레이스 배포를 위해 독립 저장소가 필요하다 (3단계 예상).
2. **변경 주체·주기가 다르다**: 예) GitOps 방식에서는 앱 코드 저장소와 배포 설정(k8s 매니페스트) 저장소를 분리하는 것이 일반적이다. CI가 이미지 태그를 설정 저장소에 커밋하고, ArgoCD가 이를 감지해 배포한다 (4단계 예상).
3. **공개 범위가 다르다**: 일부 코드만 비공개로 해야 하는 경우.

## 검토한 대안과 기각 이유

- **처음부터 서비스별 저장소 분리**: 서비스 간 계약을 바꿀 때 여러 저장소를 동시에 고쳐야 하고, CI·이슈·하네스 파일이 저장소 수만큼 늘어난다. 혼자 개발하는 상황에서는 비용만 생긴다.
- **단일 서비스(모놀리스)**: 수집 배치와 무거운 적재 작업이 API 서버와 같은 프로세스에서 돌면 서로 영향을 준다. 또한 컨테이너·k8s 배포 학습 목표와 맞지 않는다.

## 결과

- 장점
  - 데이터 계약 변경을 한 커밋으로 원자적으로 처리할 수 있다.
  - Claude Code가 한 세션에서 전체 맥락을 볼 수 있다. 서비스별 규칙은 `apps/<서비스>/CLAUDE.md`로 나눈다.
  - 경로 필터 기반 CI, 서비스별 이미지 빌드를 학습할 수 있다.
- 단점
  - 저장소가 커지면 CI 설정이 복잡해진다 → 경로 필터와 재사용 워크플로로 관리한다.
  - 서비스 경계가 흐려질 위험이 있다 → 서비스끼리 코드를 직접 import하지 않고 API·데이터 계약으로만 통신한다.
