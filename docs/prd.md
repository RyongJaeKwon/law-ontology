## 1. 문제 정의

신탁·자본시장 실무자는 법령 조문이나 유권해석을 찾을 때 법제처 사이트에서 키워드 검색을 반복해야 한다.
"이 상황에 어떤 조문이 적용되나?" 같은 자연어 질문에는 바로 답을 얻기 어렵고, 시행령·해석례까지 함께 찾으려면 시간이 많이 든다.

특히 법령은 **관계로 얽혀 있는 문서**다. 법률이 시행령에 위임하고, 다른 조문을 준용하고, 정의 조항의 용어가 여러 조문에 쓰인다.
"이 조문이 시행령에 위임한 내용까지 알려줘" 같은 질문은 비슷한 문장을 찾는 것만으로는 답할 수 없고, **관계를 따라가야** 답할 수 있다.

또한 "신탁법 제22조"처럼 **조문 번호를 직접 묻는 질문**은 의미 검색으로 맞히기 어렵다. 조문 번호는 의미가 아니라 식별자이기 때문이다.

마지막으로 금융권처럼 **외부 AI API를 쓸 수 없는 폐쇄망 환경**에서는 상용 AI 검색 서비스를 그대로 도입할 수 없다.

## 2. 타깃 사용자

| 사용자 | 주로 하는 일 |
|---|---|
| 신탁·금융 실무자 | 업무 중 관련 조문과 해석례를 빠르게 확인 |
| 법무·컴플라이언스 담당자 | 근거 조문을 정확한 출처와 함께 확인 |
| AI 에이전트(Claude Code 등) | MCP를 통해 법령 검색·관계 조회를 도구로 사용 |

## 3. 목표와 성공 지표

평가는 **정답셋 기반 지표**(검색 정확도)와 **정답 없이 재는 지표**(답변 품질)를 함께 쓴다.
점수가 떨어지면 원인 구간을 알 수 있도록 **질문 해석 → 검색 → 생성** 3단계로 나눠 측정한다.

| 목표 | 지표 | 목표치 |
|---|---|---|
| 정확한 근거 검색 | 정답셋 기준 Recall@5 (정답 조문이 상위 5개 안에 포함되는 비율) | 80% 이상 |
| 관계 질문 대응 | 관계형 문항([G]·[H])에서 하이브리드 검색의 Recall@5가 벡터 단독 대비 향상 | +15%p 이상 |
| 조문 직접 조회 | "법령명 + 제N조" 형태 질문에서 해당 조문이 1위로 나오는 비율 | 100% |
| 근거 없는 답변 방지 | Faithfulness (답변의 각 주장이 검색 근거로 뒷받침되는 비율) | 0.85 이상, **미달 시 다른 점수와 무관하게 실패** |
| 질문 의도 충족 | Answer Relevancy | 0.75 이상 |
| 검색 결과 품질 | Context Precision (관련 근거가 상위에 오는가) | 0.70 이상 |
| 신뢰할 수 있는 답변 | 출처(조문·해석례 링크)가 포함된 답변 비율 | 100% |
| 응답 속도 | 질문부터 첫 응답 토큰까지의 시간(p95) | 3초 이내 |
| 폐쇄망 대응 | 설정 변경만으로 외부 API ↔ 자체 서빙 모델 전환 | 코드 수정 없이 가능 |

- LLM이 채점하는 지표는 같은 문항을 3회 반복해 분산을 함께 기록하고, 분산이 큰 문항은 "신뢰 낮음"으로 따로 관리한다.
- 목표치는 초기값이다. 1단계에서 기준선을 측정한 뒤 조정하되, **조정 시에는 이유를 변경 이력에 남긴다.**

## 4. 유저 스토리

- 실무자로서, 자연어로 질문하면 **관련 조문과 해석례를 근거와 함께** 받고 싶다. 그래야 답변을 믿고 업무에 쓸 수 있다.
- 실무자로서, "신탁법 제22조"처럼 **조문 번호로 물으면 그 조문 원문을 정확히** 받고 싶다.
- 실무자로서, 답변에 나온 조문을 **클릭해 원문을 바로 확인**하고 싶다.
- 실무자로서, 어떤 조문을 볼 때 **위임된 시행령 조문, 준용 조문, 관련 해석례를 함께** 보고 싶다.
- 실무자로서, 조문에 나온 법률 용어의 **정의 조항을 바로 확인**하고 싶다.
- 실무자로서, 근거를 찾지 못한 경우에는 지어내지 말고 **"찾지 못했다"고 답해주길** 원한다.
- 개발자로서, Claude Code에서 **MCP로 법령을 검색하고 조문 관계를 조회**하고 싶다.
- 운영자로서, 문서를 수집할 때 **개인정보가 포함된 문서를 자동으로 걸러내고** 싶다.
- 운영자로서, 법령이 개정되어도 **이전 버전을 잃지 않고** 지식베이스를 갱신하고 싶다.

## 5. MVP 범위

### 포함
- **데이터**
  - 신탁법, 신탁법 시행령
  - 자본시장과 금융투자업에 관한 법률(자본시장법), 같은 법 시행령·시행규칙
  - 위 법령에 관한 법제처 법령해석례
- **수집 파이프라인**: 법제처 Open API 수집 → 개인정보 검사 게이트 → 조문 구조 분해 → 청킹 → 임베딩
- **법령 온톨로지**: 아래 관계를 모델링한다
  - 계층: 법령 → 조 → 항 → 호 → 목
  - 위임: 법률 조문 → 시행령·시행규칙 조문
  - 인용·준용: 조문 → 조문
  - 정의: 정의 조항 → 용어 → 그 용어가 쓰인 조문
  - 해석: 해석례 → 조문
- **그래프 DB**: 온톨로지에 따라 법령 지식 그래프 구축
- **검색**: 의미 검색 + 키워드 검색 + 그래프 탐색 하이브리드, 그리고 **조문 번호 질문의 직접 조회 경로**
- **답변 생성**: 출처가 포함된 답변, 근거가 없으면 답변 거부
- **Redis**: 시맨틱 캐시(유사 질문 응답 재사용), 요청 제한(rate limit)
- **웹 채팅 UI** (관련 조문 관계 표시 포함)
- **MCP 서버** (검색·조문 조회·관계 조회 도구 제공)
- **평가**: 정답셋(50~100문항, 문항마다 유형 [V] 벡터 / [G] 그래프 / [H] 혼합 표시)과 자동 평가 스크립트

### 제외 (MVP 이후 검토)
- 판례
- 회원가입·로그인
- 시점별 법령 조회 화면 (단, 데이터 모델은 개정 이력을 보존할 수 있게 설계한다 — ADR 0003)
- 위 법령 외의 다른 법령
- 온톨로지 표준 형식(OWL/RDF) 준수 — MVP는 그래프 DB의 속성 그래프 모델로 시작
- LLM 기반 관계 추출 — MVP는 API 구조 정보와 규칙(정규식)으로 추출한다

## 6. 제약사항

- **장비**: 로컬 MacBook M4 Pro / RAM 16GB → 임베딩만 로컬에서 실행하고, LLM은 OpenAI 호환 API를 사용
- **메모리**: 로컬에서 Postgres, Qdrant, Neo4j, Redis, 애플리케이션을 함께 띄워야 하므로 각 컨테이너의 메모리 상한을 설정한다.
- **예산**: AWS 월 2~5만 원 이내, LLM API 비용 별도
- **시간**: 주 11~18시간, 전체 약 5~6개월
- **데이터**: 공개 데이터(법제처 Open API)를 사용한다.
- **법적 고지**: 서비스는 법률 자문이 아니며, 답변 화면에 원문 확인을 권고하는 안내를 표시한다.

- [ ] 부동산등기법을 범위에 넣을 것인가? (신탁등기 관련 법령 간 인용이 생겨 그래프 실험에 유리)
- [ ] 해석례 범위: 법제처 법령해석례만 포함할지, 금융위원회 유권해석도 포함할지
