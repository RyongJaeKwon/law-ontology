# 0003. 조문 정식 키와 결정론적 청크 ID

- 상태: 승인
- 날짜: 2026-11-12

## 맥락

Postgres·Qdrant·Neo4j 세 저장소(ADR 0001)를 하나의 조문으로 묶으려면 **공통 식별자**가 필요하다.
식별자 설계를 잘못하면 그래프 품질이 무너진다. 실무에서 흔히 겪는 실패는 두 방향이다.

1. **식별자를 무작위 값(UUID v4)으로 만드는 경우**
   같은 대상이 적재할 때마다 새 노드가 된다. 문서를 한 건씩 적재하면 같은 개념이 문서마다 따로 생겨 **그래프가 문서별 섬으로 쪼개진다.** 커뮤니티 탐지 같은 그래프 분석도 의미를 잃는다.
2. **이름(문자열)만으로 합치는 경우**
   서로 다른 법령의 "제6조"가 하나의 노드로 **잘못 합쳐진다.**

또한 법령은 **개정**된다. 개정 후에도 이전 조문을 잃지 않아야 하고, 같은 입력을 다시 적재해도 중복이 생기지 않아야 한다(멱등성).

## 결정

### 1. 정식 키(canonical key)

모든 법령 단위는 **법령 식별자 + 구조 위치**로 만든 정식 키를 갖는다. 번호는 법제처 API가 제공하는 구조 정보에서 가져오며, 텍스트에서 추측하지 않는다.

| 단위 | 정식 키 형식 | 예시 |
|---|---|---|
| 법령 | `law:{법령ID}` | `law:001234` |
| 조 | `law:{법령ID}/art:{조}[-{가지}]` | `law:001234/art:22`, `law:001234/art:31-2` (제31조의2) |
| 항 | `.../art:{조}/para:{항}` | `law:001234/art:22/para:1` |
| 호 | `.../para:{항}/item:{호}` | `law:001234/art:22/para:1/item:2` |
| 목 | `.../item:{호}/sub:{목}` | `.../item:2/sub:1` (가목 = 1) |
| 용어 | `term:{법령ID}:{정규화된 용어}` | `term:001234:수탁자` |

- 법령 식별자는 **개정과 무관하게 유지되는 법제처 법령 ID**를 쓴다. 개정마다 바뀌는 일련번호는 **버전 속성**으로 따로 둔다. (두 값의 실제 동작은 API 키 발급 후 확인하고, 다르면 이 ADR을 대체한다.)
- 용어는 법령마다 정의가 다를 수 있으므로 **법령 식별자를 포함**한다. 법령을 넘나드는 같은 용어의 연결은 별도 관계(`SAME_TERM_AS`)로 표현한다.

### 2. 버전과 유효기간

- 노드와 청크는 `valid_from`(시행일), `valid_to`(다음 개정 시행일 또는 null), `status`(current / expired)를 갖는다.
- 개정이 일어나면 **삭제하지 않고**, 새 버전을 추가(INSERT)하고 이전 버전을 만료(EXPIRE: `valid_to` 설정, `status=expired`) 처리한다.
- 기본 검색은 `status=current`만 대상으로 한다. 이렇게 하면 시점별 조회 화면은 MVP 이후에 데이터 모델 변경 없이 추가할 수 있다.

### 3. 결정론적 청크 ID

- 청크 ID = **UUID v5**(고정 네임스페이스, `정식 키 + "@" + 버전`)
- 같은 조문의 같은 버전은 언제 적재해도 **같은 ID**가 나온다 → Postgres `ON CONFLICT`, Qdrant upsert, Neo4j `MERGE`로 재실행해도 중복이 생기지 않는다.
- Qdrant point ID = 청크 ID. 세 저장소 모두 이 값으로 조인한다.

### 4. 관계 추출과 검증 게이트

- **구조·명시적 관계는 결정론으로 추출한다**: 계층(조→항→호→목)은 API 구조로, 명시 인용("제N조", "같은 법 제N조", "시행령 제N조")은 정규식으로.
- 인용 표현에 법령명이 없으면(예: "제5조에 따라") **그 조문이 속한 법령으로 보완**해 정식 키로 바꾼다.
- 정식 키로 바꿀 수 없는 인용은 버리지 않고 **미해결 참조**(`UnresolvedRef` 노드)로 남겨, 이후 사전·규칙 보강의 대상으로 삼는다.
- MVP 이후 LLM으로 관계를 추출할 때는, LLM이 제안한 관계의 양 끝이 **실제 존재하는 정식 키로 해결될 때만 채택**한다.
- Neo4j 적재 전에 **무결성 검사**를 한다: 양 끝 노드가 없는 엣지, 자기 자신을 가리키는 엣지, 허용되지 않은 (노드 타입, 관계, 노드 타입) 조합.
- 그래프 적재 스크립트는 **기본이 dry-run**이고, 명시적 옵션(`--apply`)을 줄 때만 실제로 반영한다.

## 검토한 대안과 기각 이유

- **UUID v4(무작위)**: 재적재 시 중복이 생기고 그래프가 파편화된다.
- **이름 기반 병합**: 법령이 다른 동명 조문·용어가 잘못 합쳐진다.
- **DB 시퀀스(자동 증가 번호)**: 저장소마다 번호가 달라 조인 키로 쓸 수 없고, 재구축하면 값이 바뀐다.
- **개정 시 삭제 후 재적재**: 단순하지만 개정 이력을 잃고, 세 저장소에 삭제를 전파해야 한다.

## 결과

- 장점
  - 재적재가 안전하다(멱등). 실패한 적재를 그냥 다시 돌리면 된다.
  - 그래프가 법령 구조대로 정확히 연결되고, 동명 조문 혼동이 없다.
  - "신탁법 제22조" 같은 질문을 정식 키 조회로 바로 처리할 수 있다.
  - 개정 이력을 보존하므로 시점별 조회로 확장할 수 있다.
- 단점
  - 정식 키 형식을 바꾸면 전체 재적재가 필요하다 → 형식을 바꿀 때는 새 ADR로 결정한다.
  - 만료된 버전이 쌓여 저장 용량이 늘어난다 → MVP 범위(법령 5개 안팎)에서는 무시할 수준이다.
  - 미해결 참조 비율을 관리해야 한다 → 적재 리포트에 미해결 참조 수를 항상 출력한다.
